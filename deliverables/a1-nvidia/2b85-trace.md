# 10DE:2B85 (RTX 5090, GB202, subsystem 1028:5305): execution path trace (A1)

Pins and labels are as in `architecture.md`: `drv@470e391`, `ogkm615` = NVIDIA open modules 615.78.08, `1401@f5a9254`. **D** = demonstrated, **P** = project claim, **H** = hypothesis.

## 0. Facts about this card, measured on this host today (D)

Read-only `nvidia-smi` on Windows, driver 610.60:
- `pci.device_id 0x2B8510DE`, `sub_device_id 0x53051028`, VBIOS `98.02.2e.80.06`
- FB total **32607 MiB**, **BAR1 total 32768 MiB** (Resizable BAR is on in the firmware: BAR1 covers all of VRAM)
- PCIe max gen 5 x16, power limit 575 W (max limit 575 W)
- `Win32_DeviceMemoryAddress` shows only `0x60000000-0x640FFFFF` and `0xA800000000+32 MB`. CIM does not list the 32 GB range, so do not use CIM to size BARs.

GB202 identity in NVIDIA source (D): `GPU_ARCHITECTURE_BLACKWELL_GB2XX = 0x01B0`, `GPU_IMPLEMENTATION_GB202 = 0x02` (`ogkm615 src/common/inc/swref/published/nv_arch.h:53,121`).

| Item | What sources show | How `drv` handles it | Risk |
|---|---|---|---|
| GPC/TPC/SM counts | Not in public headers. The `hwproject.h` for gb202 has only PRI bases (`ogkm615 gb202/hwproject.h:27-28`). | NVK queries `GR_GET_GPC_MASK` and `GR_GET_TPC_MASK` (`nvk-macos.patch:10596-10606`) | Low (D: runtime query) |
| VRAM 32 GB | 32607 MiB visible (D, nvidia-smi) | `VRAM,totalsize` is a 64-bit OSNumber (`NVRM.cpp:1450`). RAM_SIZE comes back in KB as NvU32 (32 GB = 33,554,432 KB, which fits). NVK `vram_size_B` is u64. | Low for overflow. The working set and maxBufferLength scale with VRAM (H: untested at 32 GB). |
| **BAR1 = 32 GB** (firmware ReBAR on) | D: nvidia-smi BAR1 Total 32768 MiB | `placeLargeBar1`: a BAR1 of 4 GB or more is **not resized**. It is left in place if above 4 GB, in the nub, and not holding the console (`NVRM.cpp:1102-1115`). Otherwise it is moved at full size, which needs a free 32 GB-aligned slot in the host 64-bit window (`:1154-1156`). Small-BAR path: the resize target is capped at 8 GB (`k = 13..12`, `:1052`), because "resized to 16 GB stopped during bring-up" on a 3060 and a 5080 (`:1043`, P). | **High / untested.** A 32 GB firmware BAR1 under macOS has no public test. The project only proves 8 GB (`HOW-IT-WORKS.md:85`, P). | Surface budget | `nvrmVramBudget(bar) = bar/2` for BAR1 of 4 GB or more (`NVRMFB nvrm-fb.cpp:76-81`) | 32 GB BAR1 gives a 16 GB budget, 8 GB gives 4 GB. `test_bar1_budget.py` covers up to 8 GB only (D). | Low/medium |
| Decode/encode engine count | GB202: 4 NVDEC, 4 NVENC (class-table ceiling). GB206: 1/1 (D) | Closed libraries choose the engine. #105 shows they once hard-coded instance 0 (P). | **#425: open.** Floor-swept instances on 5090 boards are unknown. |
| Display heads / multi-monitor | Same `NVCA70` display class on GB202 and GB206 (D) | `nvfbheads=4` boot-arg. Heads with no monitor log `kapiInit failed` (P: #51) | Medium: 3-display hot-plug spin on a 5080 (#454, P, open) |

## 2. Device-ID / chip-name logic that 2B85 passes through (D)

- `install.sh:165-168`: 2B85 is in the list, so the installer proceeds.
- `NVRM::publishGpuProfile` (`NVRM.cpp:1266-1307`): arch 0x1B0, impl 2 gives `gen="Blackwell"`, chip `"GB" + "2" + "02"` = `GB202`, `native-shaders sm_120`, `video-layout blackwell`.
- NVK: chipset `0x1b2 >= 0x1b0` gives sm 120 (`nvk-macos.patch:10199`).
- Vendor compiler: the `"GB20"` prefix gives 12.0 (`NVMTLVendorCompiler.m:59`).
- Decode service with no profile: `0x2b85` is in `[0x2b00, 0x3000)`, so Blackwell (`NVMTLDevice.m:468`).

None of these has a GB202-specific branch, and none fails for 2B85. All of this is static reading. Nothing has been run on a GB202.

## 3. Issue #425 analysis

- P: the report has no logs. "Report ID 111" is not a Send-logs ID format (IDs look like `NM-XXXXXXXX`, see #105).
- D: the Blackwell decoder library is chosen for 2B85 (see above). The likely failure points are outside the open source: the closed `libnvdec_*` engine selection, the sandbox and delegation rules (#175, #349, #414: QuickTime and Safari fall back to AppleH264SW), or the decode service not registering.
- **H (most specific, testable):** as with NVENC on GB203 (#105), the 5090's NVDEC0 may be floor-swept, or the library may pick an instance or class that RM refuses on GB202. This cannot be decided without the engine list from a 5090, which is why the A1 patch adds `nvdec-instances` and `nvenc-instances` to `nvrm-gpu-profile` and logs the raw `GET_ENGINES_V2` list.
- Other hypotheses that equally fit the report: (i) the app is a sandboxed Apple app and AppleH264SW is used (#414 pattern). (ii) "Choppy" playback is display pacing at 120 Hz (#302 pattern), not decode. The diagnostic in `macos-gpu-tests.md` T-MEDIA-1..3 tells these apart.

## 4. Coexistence with the active Arrow Lake iGPU (8086:7D67)

| Question | Answer | Label |
|---|---|---|
| What is NMIntelFB? | A framebuffer that adopts the firmware-lit pipe (linear XRGB8888 only) on Intel display versions 12-20. It writes no display registers. Frames rendered on NVIDIA are copied into its surface as NVAccel head 4. | D: `intelfb.cpp:1-11,293-391` |
| Does it support 7D67? | 7D67 is in its table as display version 14 (`display_ids.inc:53`, generated from Linux `pciids.h`) | D |
| Is it installed by default? | **No.** `install.sh:10` installs `NVRM NVAccel NVRMFB NVRMAGDC` (+ the optional selector). NMIntelFB ships through 1401's "AMD/Intel test program" | D (install.sh), P (CHANGELOG 2.0.4) |
| Fit for this desktop | It was designed for **laptop panels**. It sets `built-in = true` (`intelfb.cpp:387`), takes **only the first lit pipe** (`:295-296`), cannot set modes or hot-plug, and only works if the firmware lit the iGPU output in linear XRGB. On this desktop the iGPU drives an external 4K monitor at 59 Hz, which would appear as a "built-in" display, at whatever mode GOP lit. | D (code), H (behaviour here) |
| Sleep/wake on the iGPU | NMIntelFB does not do the IOGraphics wake work | P: `SLEEP-WAKE.md` "Not covered" |
| NVPrimarySelector / AUTO-PRIMARY-GPU | Opt-in (`NM_PRIMARY_GPU=1`, `nvselector=1`). It marks the NVIDIA GPU **that owns the firmware console**. If the firmware console is on the iGPU, no NVIDIA card owns it and no marker is set. With a single NVIDIA GPU the selector is unnecessary, because default matching takes the only NVIDIA device. | P: `AUTO-PRIMARY-GPU.md:3-16`. H: outcome with the console on the iGPU |
| BAR1 and boot console | `placeLargeBar1` moves or keeps BAR1 depending on whether the **console** is inside it (`NVRM.cpp:1104-1115`, `:1109`). If the console is on the iGPU, a firmware-placed 32 GB BAR1 above 4 GB is left in place. That case is not tested. | D (code), H (outcome) |
| WhateverGreen | README asks for `gfxrst=4` when WhateverGreen is present for an Intel/AMD GPU (boot-screen copy use-after-free) | P: `README.md:122-123` |
| macOS native iGPU driver | NMIntelFB's own header says macOS has no driver for display version 12-20 Intel GPUs. A desktop Arrow Lake iGPU therefore gets no acceleration and, without NMIntelFB, at most IONDRV basic framebuffer | P |

**Recommendation (H):** for first bring-up, move the iGPU-attached monitor to the 5090 or leave it unplugged, set the BIOS primary display to PEG, and leave NMIntelFB uninstalled. Add the iGPU display only after the 5090 path passes T-BOOT and T-DISP in `macos-gpu-tests.md`.
